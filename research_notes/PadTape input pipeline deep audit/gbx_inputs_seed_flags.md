Bottom line up front:
1. TM2020 inputs live in `CGameCtnGhost` skippable chunk **0x0309201D** ("player input data", chunk version 4 in TM2020) as one or more `PlayerInputData` archives: `{int Version (=12 in TM2020), int (unnamed), TimeInt32? StartOffset, int Ticks, byte[] Data}`; `Data` is an LSB-first **bit-packed per-10 ms-tick stream**, not an event list. **[SRC]**
2. There is no input named "seed" in any parser. The only "seed" is `CGameCtnGhost.Validate_ValidationSeed`, a 32-bit int in the validation chunk **0x03092025** (TM2020 chunk version 1; also 0x03092019 in TMF and 0x0309202D in TM2020). Its semantics are not documented by any parser; the only Nadeo-side evidence is the TMF dedicated-server option `UseChangingValidationSeed` ("whether the game should use a variable validation seed"). **[SRC]/[DOC]/[UNVERIFIED semantics]**
3. No parser emits an input named "flags". The closest thing is the raw 33/34-bit **`States`** word (GBX.NET `TrackmaniaInputChange.States`, Ghosts++ `IInputChange.get_States()`). If the user's `flags` is that word, 4128 = 0x1020 = bit 12 | bit 5, and the parsers do not agree on what those bits mean (GBX.NET: bit 12 = Jump, bit 5 = GunTrigger [character only]; Ghosts++: bits 5–6 = horn-packed) — and its low nibble 0 would mean "NotStarted", which contradicts the following vehicle inputs. So treat the user's `flags` as **[UNVERIFIED]** / not the raw states word, or from a tool with its own mapping. **[SRC]**
4. No public tool was found that emits or consumes the exact lowercase vocabulary `seed/accel/brake/steer/flags` with a `0 seed N` header line. **[GAP]**

## Q1. Which GBX chunk(s) store TM2020 inputs (CGameCtnGhost / CGameCtnReplayRecord / CPlugEntRecordData)?

### Takeaway
TM2020 inputs are in `CGameCtnGhost` chunk `0x0309201D` (`PlayerInputs`, list of `PlayerInputData`), a tick-based bitstream. The legacy 9-byte event list (`CInputEventsStore::Archive`) in `0x03092011/0x03092019/0x03092025` is TMU→TM2; in TM2020 `0x03092025` v1 still carries the validation struct and the `ValidationSeed`, with the event list expected empty. `CPlugEntRecordData` (`0x0911F000`) stores vehicle-state samples, not inputs.

## Q2. Exact per-event layout: timestamps, name indexing, value encoding (steer, accel, brake)

### Takeaway
TM2020 has no per-event records: each 10 ms tick is encoded as a variable-length group of bits (LSB-first) with "same as previous" flags; steer is a signed 8-bit value (−127..127 nominal, `Value/127f`), accelerate and brake are single bits; a 33-bit (version 11) or 34-bit (version 12) `states` word carries buttons. Decoded "inputs" are change events synthesised by the parser (`time = tick*10 ms + StartOffset`), so several can share a timestamp.

- **[INFERENCE]** The user's steer vocabulary (−127/0/127) matches `SteerTM2020.Value` (sbyte) exactly, and `accel 1/0`, `brake 1/0` match the `Accelerate`/`Brake` bits. The user's format is therefore consistent with a dump of a TM2020 `PlayerInputData` decode (GBX.NET-style or Ghosts++-style), not of the legacy 9-byte event list (which would have 16-bit analog values).
- **[INFERENCE]** Because every tick that changes emits separate steer/accel/brake records at the same `time`, lines like `-1500 accel 1`, `-1500 brake 0`, `-1500 steer 0` at one timestamp are the expected shape of a "first full state" tick.

### Gaps
- No parser documents whether a steer value of −128 can occur (GBX.NET normalises by 127 and the wiki says −127..127; the raw type is sbyte).
- The purpose of the unnamed `int` header field and of `mouseAccuX/Y` for vehicle play is undocumented.

## Q3. Is there a "seed" field? Where, what size, what do parsers think it means?

### Takeaway
Yes: GBX.NET `CGameCtnGhost.Validate_ValidationSeed` (`int?`, 32-bit), read in chunk `0x03092019` (TMF), `0x03092025` (TM2 v0 via 019; TM2020 v1 directly, after the validation struct and before `SteeringWheelSensitivity`), and `0x0309202D` (TM2020). No parser comments on its meaning; it is **not** used by any decoder as an XOR/scramble key. Nadeo's TMF dedicated server exposes a "changing validation seed" option, which is the only semantic hint found.

## Q5. Timestamps: first input time, countdown offset, quantisation, shared timestamps, end-of-race handling; known decoder limitations

### Takeaway
Times are `tick × 10 ms + StartOffset` (GBX.NET) or `tick × 10 ms` (Ghosts++ ignores `StartOffset`); 10 ms is the only resolution. Multiple records may share a timestamp. There is no finish marker in the TM2020 bitstream (the `_FakeFinishLine`/`_FakeIsRaceRunning` names belong to the legacy TMU–TM2 event list); decoding runs for all `Ticks`, so inputs after the finish appear. Known limitations: version-11 (33-bit) runs, "car transformation", mouse-bound inputs, "rare input state bugs" fixed as late as July 2026, unsupported "float-based steering" kinds.

- **[INFERENCE]** The input bitstream is what the game's input layer produced after binding/deadzone/quantisation (`InputQuant_*`), i.e. post-processing relative to the controller, but pre-physics; the `CPlugEntRecordData` steer/gas/brake bytes are the vehicle-vis values after the physics step. Cross-checking the two is feasible (compare `SteerTM2020.Value/127` with `((steer/255)-0.5)*2` at nearest sample time) but the sample stream is coarser and interpolated. Mark any mismatch < one sample interval as expected.

### Gaps
- No source explains the exact `InputQuant_*` functions (deadzone, curve) applied before storing steer as i8.
- No Nadeo statement on whether the in-game ghost "inputs" HUD reads the bitstream or the vis state.

## Q8. Round-trip (parse → rewrite) for TM2020, documented loss, and input-to-ghost tools

### Takeaway
No public tool re-encodes TM2020 inputs. GBX.NET keeps `PlayerInputData.Data` as opaque bytes (round-trips unchanged but offers no encoder); its wiki says modifying TM2020 inputs "isn't easy" and `CGameCtnReplayRecord` is write-unsupported. TM2020 samples became writable in 2026. No "ghost from inputs" tool exists; the only TM2020 TAS project has playback "not implemented".

### Cited Findings
- **[SRC]** `PlayerInputData` archive stores `data Data` raw; the decoders (`ProcessTrackmaniaInputs`, `ProcessTrackmaniaInputChanges`) are read-only; no `Write`/encode method exists for the bitstream in the clone (grep of `Src/GBX.NET/Engines/Game/CGameCtnGhost.PlayerInputData.cs` at `edbcf1b7`). **[DOC]** wiki: modifying TM2020 inputs "isn't easy to do, and there's generally no good reason to." — [GBX.NET wiki](https://raw.githubusercontent.com/wiki/BigBang1112/gbx-net/Extracting-input-data-from-ghosts.md)
