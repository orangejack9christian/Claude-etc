# Windows timing/scheduling, focus, hooks and IPC for a packaged Python GUI + keyboard-worker process (Windows 10/11, as of 2026-10-20)

Scope: a PyInstaller/Nuitka-packaged Python desktop GUI that spawns a separate Python "keyboard worker" process injecting timed keystrokes (~10 ms granularity) into a game, talking to the GUI over a pipe, detecting physical keyboard takeover with a WH_KEYBOARD_LL hook, and stopping cleanly on focus loss.

## KQ1. Timer resolution and sleep accuracy (timeBeginPeriod, high-resolution waitable timers, Sleep(1), busy-wait, priorities, MMCSS)

### Takeaway
Since Windows 10 2004 `timeBeginPeriod` is per-process ("processes which have not called this function" get no guarantee), and since Windows 11 a process whose windows are occluded/minimized/invisible-and-inaudible may have its timer-resolution request ignored unless it opts out via `SetProcessInformation(ProcessPowerThrottling, PROCESS_POWER_THROTTLING_IGNORE_TIMER_RESOLUTION, StateMask=0)`. The better primitive for a ~10 ms worker loop is `CreateWaitableTimerExW(CREATE_WAITABLE_TIMER_HIGH_RESOLUTION)` (Win10 1803+), which CPython 3.11+ already uses inside `time.sleep()`; published measurements show ~0.5–1.5 ms overshoot for 1 ms-class sleeps versus ~15.6 ms at default resolution.

### Cited Findings

**timeBeginPeriod semantics (per-process since 2004; Win11 background behaviour)**
- [DOC] "Prior to Windows 10, version 2004, this function affects a global Windows setting. For all processes Windows uses the lowest value (that is, highest resolution) requested by any process. Starting with Windows 10, version 2004, this function no longer affects global timer resolution. For processes which call this function, Windows uses the lowest value (that is, highest resolution) requested by any process. For processes which have not called this function, Windows does not guarantee a higher resolution than the default system resolution." — [timeBeginPeriod, Microsoft Learn (ms.date 2018-12-05, updated 2024-02-22)](https://learn.microsoft.com/en-us/windows/win32/api/timeapi/nf-timeapi-timebeginperiod)
- [DOC] "Starting with Windows 11, if a window-owning process becomes fully occluded, minimized, or otherwise invisible or inaudible to the end user, Windows does not guarantee a higher resolution than the default system resolution. See SetProcessInformation for more information on this behavior." — same page.
- [DOC] "Setting a higher resolution can improve the accuracy of time-out intervals in wait functions. However, it can also reduce overall system performance ... High resolutions can also prevent the CPU power management system from entering power-saving modes. Setting a higher resolution does not improve the accuracy of the high-resolution performance counter." — same page.
- [DOC] "You must match each call to timeBeginPeriod with a call to timeEndPeriod, specifying the same minimum resolution in both calls." — same page.
- [DOC] SetProcessInformation / ProcessPowerThrottling: "When a process opts into enabling PROCESS_POWER_THROTTLING_IGNORE_TIMER_RESOLUTION, any current timer resolution requests made by the process will be ignored. Timers belonging to the process are no longer guaranteed to expire with higher timer resolution, which can improve power efficiency. After explicitly disabling PROCESS_POWER_THROTTLING_IGNORE_TIMER_RESOLUTION, the system remembers and honors any previous timer resolution request by the process. By default in Windows 11 if a window owning process becomes fully occluded, minimized, or otherwise non-visible to the end user, and non-audible, Windows may automatically ignore the timer resolution request and thus does not guarantee a higher resolution than the default system resolution." — [SetProcessInformation, Microsoft Learn (ms.date 2024-10-31, updated 2025-07-01)](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation)
- [DOC] The same page gives the opt-out example: `ControlMask = PROCESS_POWER_THROTTLING_IGNORE_TIMER_RESOLUTION; StateMask = 0;` → "Always honor Timer Resolution Requests." and `ControlMask = StateMask = PROCESS_POWER_THROTTLING_IGNORE_TIMER_RESOLUTION` → "Ignore Timer Resolution Requests." `Version` must be `PROCESS_POWER_THROTTLING_CURRENT_VERSION`. Minimum supported client for SetProcessInformation: Windows 8. — same page.
- [DOC] Note: the `PROCESS_POWER_THROTTLING_STATE` structure reference page itself only lists `PROCESS_POWER_THROTTLING_EXECUTION_SPEED` in its tables; `PROCESS_POWER_THROTTLING_IGNORE_TIMER_RESOLUTION` is documented only on the SetProcessInformation page. — [PROCESS_POWER_THROTTLING_STATE (updated 2024-02-22)](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/ns-processthreadsapi-process_power_throttling_state)
- [DOC] Also on the SetProcessInformation page: `PROCESS_POWER_THROTTLING_EXECUTION_SPEED` opts into EcoQoS ("reducing CPU frequency or using more power efficient cores"); "If an application does not explicitly enable PROCESS_POWER_THROTTLING_EXECUTION_SPEED, the system will use its own heuristics to automatically infer a Quality of Service level." Setting `ControlMask = EXECUTION_SPEED, StateMask = 0` forces HighQoS. — same page.
- [MEAS][COMM] Bruce Dawson (2020-10-04), "Windows Timer Resolution: The Great Rule Change": on 2004, "calls to timeBeginPeriod from one process now affect other processes less than they used to"; the global interrupt rate still changes and `timeGetTime` still updates at that rate; processes that call `timeBeginPeriod(1)` still get what they asked for; "If a process wants a faster timer interrupt then it should be calling timeBeginPeriod itself." He measured an irregular mapping on 2004: with another process at 8 ms, `Sleep(1)` "returns after one interval about 20% of the time and after two intervals the rest" (average ≈14.5 ms). The post was later updated to note that the change is now acknowledged in the timeBeginPeriod documentation. — [randomascii.wordpress.com, 2020-10-04](https://randomascii.wordpress.com/2020/10/04/windows-timer-resolution-the-great-rule-change/)
- [MEAS][COMM] Bruce Dawson (2013-07-08), "Windows Timer Resolution: Megawatts Wasted": "The default timer resolution on Windows is 15.6 ms – a timer interrupt 64 times a second." At the default interval `Sleep(1)` waits about 15–16 ms; with the timer raised "on Windows 7+ it typically sleeps for no more than 1 ms." Power cost: ~0.3 W on his laptop; quotes Microsoft: "Some applications reduce this to 1 ms, which reduces the battery run time on mobile systems by as much as 25 percent." Recommends Sysinternals `clockres` to see the current resolution. — [randomascii.wordpress.com, 2013-07-08](https://randomascii.wordpress.com/2013/07/08/windows-timer-resolution-megawatts-wasted/)

**High-resolution waitable timers**
- [DOC] `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION` (0x00000002): "Creates a high resolution timer. Use this value for time-critical situations when short expiration delays on the order of a few milliseconds are unacceptable. This value is supported in Windows 10, version 1803, and later." No accuracy figure is documented. — [CreateWaitableTimerExW, Microsoft Learn (ms.date 2018-12-05, updated 2024-11-20)](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createwaitabletimerexw)

- [MEAS] Go runtime commit 515e6a9b (authored 2020-07-19, committed 2020-10-18, "runtime: use CreateWaitableTimerEx to implement usleep", fixes golang/go#8687) includes a C test on one machine:

  - flag off, timeBeginPeriod(1) on: 1000 µs → 742 µs; 100 µs → 893 µs; 10 µs → 414 µs; 1 µs → 920 µs
  - flag ON, timeBeginPeriod(1) on: 1000 µs → 1466 µs; 100 µs → 559 µs; 10 µs → 535 µs; 1 µs → 5 µs
  "This change will only run on systems where CREATE_WAITABLE_TIMER_HIGH_RESOLUTION flag is available. If not available, the runtime will fallback to original code that uses timeBeginPeriod." — [go.googlesource.com commit 515e6a9b](https://go.googlesource.com/go/+/515e6a9b12dfe654c86cfd070ee5d6ac144fe116)

**CPython `time.sleep` on Windows**
- [DOC] "On Windows 10 and newer the implementation uses a high-resolution timer which provides resolution of 100 nanoseconds. If seconds is zero, Sleep(0) is used." "Changed in version 3.11: On Unix, the clock_nanosleep() and nanosleep() functions are now used if available. On Windows, a waitable timer is now used." "The suspension time may be longer than requested by an arbitrary amount, because of the scheduling of other activity in the system." — [time — docs.python.org (3.x)](https://docs.python.org/3/library/time.html)
- [SRC/DOC] gh-65501 (bpo-21302): PRs #28341/#28483 "time.sleep() uses waitable timer on Windows", labelled Python 3.11. A commenter (Livius90, Windows 10, i7-10850H) measured: Py3.10 `time.sleep(0.001)` mean 15.9 ms ±350.9 µs; Py3.11 `time.sleep(0.001)` mean 1.6 ms ±339.6 µs; Py3.11 `time.sleep(0.0001)` 574.6 µs ±95.2 µs. — [github.com/python/cpython/issues/65501](https://github.com/python/cpython/issues/65501)
- [SRC/DOC] gh-89592 (bpo-45429) "Support CREATE_WAITABLE_TIMER_HIGH_RESOLUTION if possible": commit 55868f1 merged to main 2021-11-16 (PR #29203), Python 3.11; eryksun's design: if `CreateWaitableTimerExW` fails with `ERROR_INVALID_PARAMETER` with the flag set, retry without the flag (older Windows fallback). corona10 reported average sleep going from ≈0.01561 s to ≈0.0000274 s for a tiny sleep. — [github.com/python/cpython/issues/89592](https://github.com/python/cpython/issues/89592)

**Priorities and MMCSS**
- [DOC] Scheduling priorities: priority classes IDLE/BELOW_NORMAL/NORMAL/ABOVE_NORMAL/HIGH/REALTIME; "Use HIGH_PRIORITY_CLASS with care. If a thread runs at the highest priority level for extended periods, other threads in the system will not get processor time." "You should almost never use REALTIME_PRIORITY_CLASS, because this interrupts system threads that manage mouse input, keyboard input, and background disk flushing." Base-priority table: NORMAL_PRIORITY_CLASS + THREAD_PRIORITY_TIME_CRITICAL = 15; HIGH_PRIORITY_CLASS + THREAD_PRIORITY_HIGHEST = 15; REALTIME + TIME_CRITICAL = 31. — [Scheduling Priorities (ms.date 2025-07-14)](https://learn.microsoft.com/en-us/windows/win32/procthread/scheduling-priorities)
- [DOC] MMCSS: threads call `AvSetMmThreadCharacteristics`/`AvSetMmMaxThreadCharacteristics` naming a task; default tasks include "Audio", "Capture", "Distribution", "Games", "Playback", "Pro Audio", "Window Manager". `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Multimedia\SystemProfile\SystemResponsiveness` = percentage of CPU reserved for low-priority tasks (e.g. 20 → 20%); "A value of 100 disables MMCSS". Category priorities: High 23–26 ("designed for Pro Audio tasks"), Medium 16–22 ("part of the application that is in the foreground"), Low 8–15. MMCSS priority depends in part on "Whether the application is in the foreground." A "Background Only" task's threads "do not change because of a change in window focus." The "Clock Rate" guarantee was removed in Windows 7. — [Multimedia Class Scheduler Service (ms.date 2025-07-14)](https://learn.microsoft.com/en-us/windows/win32/procthread/multimedia-class-scheduler-service)

### Inferences
- [DEDUCTION] A hidden/console-less worker process on Windows 11 is exactly the "non-visible … and non-audible" case: if it relies on `timeBeginPeriod(1)` it must also call `SetProcessInformation(ProcessPowerThrottling)` with `ControlMask=IGNORE_TIMER_RESOLUTION, StateMask=0`, or its 1 ms request "may" be ignored. The doc says "may", not "will"; treat it as non-deterministic. (Whether a process that owns no window at all is affected is not stated; see Gaps.)
- [DEDUCTION] Because CPython 3.11+ `time.sleep()` already uses `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION`, a Python worker gets the Go-commit-class accuracy (≈0.5–1.5 ms overshoot) without `timeBeginPeriod`, provided the interpreter is ≥3.11 and the OS is ≥1803. Overshoot still exists; a 10 ms cadence loop should compute absolute deadlines from `time.perf_counter()` (QPC) and sleep until (deadline − guard), then optionally spin, rather than sleeping fixed 10 ms.
- [DEDUCTION] `Sleep(1)`/`WaitForSingleObject(h, 1)` are still tied to the interrupt period unless the process raised resolution (Dawson 2013/2020 + timeBeginPeriod doc); a high-resolution waitable timer is the only documented path that avoids raising the system interrupt rate.
- [DEDUCTION] `THREAD_PRIORITY_TIME_CRITICAL` in NORMAL_PRIORITY_CLASS (base 15) is the highest priority obtainable without HIGH/REALTIME class; MMCSS "Games" or "Pro Audio" are the documented route to 16–26 for a short-running input thread. The MMCSS "foreground" factor means a background worker should not expect Medium (16–22) unless the task is "Background Only"—which of the default tasks are marked Background Only is not shown on the doc page.
- [DEDUCTION] A busy-wait with QPC is the only approach immune to timer-resolution policy but costs a full core; a hybrid "sleep until deadline − ~1.5 ms, then spin" bounds both.

### Gaps
- No Microsoft figure for the accuracy of `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION`; only third-party single-machine measurements (Go commit, CPython issue comments).
- Whether the Windows 11 "occluded/minimized" timer-resolution rule applies to a process that owns no top-level window (e.g. a `CREATE_NO_WINDOW` worker) is not stated in the docs. [UNVERIFIED]
- Whether `PROCESS_POWER_THROTTLING_IGNORE_TIMER_RESOLUTION` opt-out also affects high-resolution waitable timers (as opposed to `timeBeginPeriod`-dependent waits) is not documented. [UNVERIFIED]
- Which default MMCSS tasks have `Background Only = True` is not listed on the MMCSS page.

## KQ2. Foreground/focus semantics; how a spawned worker can accidentally change foreground; detecting the game window; observing focus changes; momentary foreground changes

### Takeaway
A process can only call `SetForegroundWindow` successfully under a documented set of conditions (foreground process, started by the foreground process, received last input, etc.); merely spawning a child does not change foreground, but a console child without `CREATE_NO_WINDOW` creates a console host window that community reports show flashes and steals focus. Use `GetForegroundWindow`/`GetGUIThreadInfo(0)` for polling and `SetWinEventHook(EVENT_SYSTEM_FOREGROUND, WINEVENT_OUTOFCONTEXT)` (needs a message loop) to observe changes; UAC prompts move to a separate secure desktop on which user-level hooks/`GetAsyncKeyState` fail.

### Cited Findings

**Who may set foreground**
- [DOC] "A process can set the foreground window by calling SetForegroundWindow only if: All of the following conditions are true: The calling process belongs to a desktop application ... The foreground process has not disabled calls to SetForegroundWindow by a previous call to the LockSetForegroundWindow function. No menus are active. Additionally, at least one of the following conditions is true: The foreground lock time-out has expired (see SPI_GETFOREGROUNDLOCKTIMEOUT ...). The calling process is the foreground process. The calling process was started by the foreground process. There is currently no foreground window, and thus no foreground process. The calling process received the last input event. Either the foreground process or the calling process is being debugged." "It is possible for a process to be denied the right to set the foreground window even if it meets these conditions." "An application cannot force a window to the foreground while the user is working with another window. Instead, Windows flashes the taskbar button." — [SetForegroundWindow (ms.date 2025-10-06, updated 2025-10-07)](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow)
- [DOC] "A process that can set the foreground window can enable another process to set the foreground window by calling the AllowSetForegroundWindow function. The process specified ... loses the ability to set the foreground window the next time that either the user generates input, unless the input is directed at that process, or the next time a process calls AllowSetForegroundWindow ..." — same page.
- [DOC] The function's own description: "The system assigns a slightly higher priority to the thread that created the foreground window than it does to other threads." — same page.

**Console child windows / creation flags**
- [DOC] `CREATE_NO_WINDOW` (0x08000000): "The process is a console application that is being run without a console window. Therefore, the console handle for the application is not set. This flag is ignored if the application is not a console application, or if it is used with either CREATE_NEW_CONSOLE or DETACHED_PROCESS." `DETACHED_PROCESS` (0x00000008): "For console processes, the new process does not inherit its parent's console (the default). The new process can call the AllocConsole function at a later time ... This value cannot be used with CREATE_NEW_CONSOLE." `CREATE_NEW_CONSOLE` (0x10): "The new process has a new console, instead of inheriting its parent's console." — [Process Creation Flags (ms.date 2025-07-14)](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags)
- [DOC] Python: `subprocess.CREATE_NO_WINDOW` ("a new process will not create a window", added 3.7), `subprocess.DETACHED_PROCESS` (added 3.7), `STARTUPINFO.dwFlags |= STARTF_USESHOWWINDOW` with `wShowWindow = SW_HIDE` ("Hides the window. Another window will be activated."; used internally when `shell=True`). — [subprocess — docs.python.org](https://docs.python.org/3/library/subprocess.html)
- [COMM] Search-result snippets (pages not all opened): a Sublime Text forum thread and a Mercurial commit describe a console host window briefly appearing in front of the GUI and stealing focus when launching a console program from a GUI app; the Mercurial fix switched to `CREATE_NO_WINDOW`; the Sublime thread notes `STARTF_USESHOWWINDOW/SW_HIDE` can also hide windows of GUI children. The Mercurial page itself returned an access-denied page when fetched, so this is **search snippet only**: [forum.sublimetext.com thread](https://forum.sublimetext.com/t/window-loses-focus-when-running-subprocess/44022), [Mercurial changeset e780fb37168b](https://repo.mercurial-scm.org/hg/rev/e780fb37168b). Treat as community inference consistent with the documented flag semantics.

**Detecting the game window / focus**
- [DOC] `GetFocus` "returns the window with the keyboard focus for the current thread's message queue. If GetFocus returns NULL, another thread's queue may be attached to a window that has the keyboard focus." "Use the GetForegroundWindow function to retrieve the handle to the window with which the user is currently working." "To get the window with the keyboard focus on the foreground queue or the queue of another thread, use the GetGUIThreadInfo function." — [GetFocus (updated 2025-07-01)](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getfocus)
- [DOC] `GetGUIThreadInfo(idThread, &gui)`: "If this parameter is NULL, the function returns information for the foreground thread." - [DOC] `WM_ACTIVATEAPP` is "Sent when a window belonging to a different application than the active window is about to be activated. **WinEvent hook for foreground changes**
- [DOC] `EVENT_SYSTEM_FOREGROUND` (0x0003): "The foreground window has changed. The system sends this event even if the foreground window has changed to another window in the same thread. **Momentary foreground changes: UAC / secure desktop**
- [DOC] UAC "Switch to the secure desktop when prompting for elevation" is Enabled by default on client computers (applies to Windows 10 and 11): "The secure desktop's primary difference from the user desktop is that only trusted processes running as SYSTEM are allowed to run here (that is, nothing is running at the user's privilege level)." — [UAC: Switch to the secure desktop (archived; updated 2026-04-27)](https://learn.microsoft.com/en-us/windows/security/threat-protection/security-policy-settings/user-account-control-switch-to-the-secure-desktop-when-prompting-for-elevation)

### Inferences
- [DEDUCTION] Spawning the worker with `subprocess.Popen(..., creationflags=CREATE_NO_WINDOW)` (and, for a `--windowed` PyInstaller parent, possibly also `STARTUPINFO(dwFlags=STARTF_USESHOWWINDOW, wShowWindow=SW_HIDE)`) is the documented way to avoid a console host window; a console host window appearing is the only mechanism in the cited material by which a child could disturb foreground without calling `SetForegroundWindow`. If the worker binary is itself a windowed (non-console) executable, `CREATE_NO_WINDOW` is ignored by definition and no console is created.
- [DEDUCTION] Because "the calling process was started by the foreground process" is a documented grant, a worker spawned while the GUI is foreground would itself be *permitted* to call `SetForegroundWindow`; the worker must therefore simply never call it (nor `SetActiveWindow`/`ShowWindow` on anything) to be safe.
- [DEDUCTION] For "stop on focus loss", the robust design is: a WinEvent hook on `EVENT_SYSTEM_FOREGROUND` (and `EVENT_SYSTEM_DESKTOPSWITCH` to catch UAC/secure-desktop switches) running on the same message-loop thread as the WH_KEYBOARD_LL hook, cross-checked with `GetForegroundWindow()` + `GetWindowThreadProcessId()` against the game's PID, because the event-constants doc warns the hwnd/thread info can be transient "when a window is losing activation".
- [DEDUCTION] During a UAC secure-desktop prompt the worker's `SendInput`, LL hook, and `GetAsyncKeyState` will all be ineffective (not on the active desktop); the worker should treat `EVENT_SYSTEM_DESKTOPSWITCH` or a `GetAsyncKeyState`==0-for-everything condition as "focus lost" and release keys when the desktop returns (releasing on the secure desktop will not reach the game).

## KQ3. Low-level keyboard hooks: message loop, injected flags, dwExtraInfo, hook timeout removal, Python libraries

### Takeaway
`WH_KEYBOARD_LL` is delivered by message to the installing thread, which therefore must pump messages; `KBDLLHOOKSTRUCT.flags` bit 4 (`LLKHF_INJECTED`, 0x10) marks any injected event and bit 1 (`LLKHF_LOWER_IL_INJECTED`, 0x02) marks injection from a lower-integrity process. Windows silently removes a hook that exceeds `LowLevelHooksTimeout` (registry; Microsoft documents no default, AutoHotkey docs say 300 ms, Win10 1709+ caps it at 1000 ms) with no notification. `pynput` (1.8.2) surfaces an `injected` boolean from these flags; `keyboard` (0.13.5) drops events whose flags have both 0x10 and 0x20 set and sends single keys via `keybd_event` with `dwExtraInfo=0`, so it does not tag its own injections.

### Cited Findings
- [DOC] "This hook is called in the context of the thread that installed it. The call is made by sending a message to the thread that installed the hook. Therefore, the thread that installed the hook must have a message loop." — [LowLevelKeyboardProc (ms.date 2025-07-14)](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc)
- [DOC] "When this callback function is called in response to a change in the state of a key, the callback function is called before the asynchronous state of the key is updated. Consequently, the asynchronous state of the key cannot be determined by calling GetAsyncKeyState from within the callback function." — same page.
- [DOC] Timeout: "The hook procedure should process a message in less time than the data entry specified in the LowLevelHooksTimeout value in the following registry key: HKEY_CURRENT_USER\Control Panel\Desktop. The value is in milliseconds. If the hook procedure times out, the system passes the message to the next hook. However, on Windows 7 and later, the hook is silently removed without being called. There is no way for the application to know whether the hook is removed." "Windows 10 version 1709 and later: The maximum timeout value the system allows is 1000 milliseconds (1 second). The system will default to using a 1000 millisecond timeout if the LowLevelHooksTimeout value is set to a value larger than 1000." — same page. **The page states no default value.**
- [DOC] Same page recommendation: "If the application must use low level hooks, it should run the hooks on a dedicated thread that passes the work off to a worker thread and then immediately returns. In most cases where the application needs to use low level hooks, it should monitor raw input instead."
- [COMM] AutoHotkey v1 docs (`#IfTimeout`): "If LowLevelHooksTimeout is not defined, the default timeout is 300 ms." ### Inferences
- [DEDUCTION] A physical-takeover detector should run the LL hook on a dedicated thread whose callback only reads `flags`, `vkCode`, `time`, and posts to a queue, never doing pipe I/O or Python-level heavy work, because any callback stall ≥ (300 ms assumed default, ≤1000 ms) silently uninstalls the hook with no error — the worker would then stop detecting physical input while believing it still is. A watchdog that periodically verifies the hook is alive (e.g. by injecting a sentinel key with a unique `dwExtraInfo` and expecting to see it in the hook) is the only self-check available, since "There is no way for the application to know whether the hook is removed."
- [DEDUCTION] To distinguish *our* injections from *other* injections (e.g. game overlays, AutoHotkey), use `SendInput` with a process-specific `dwExtraInfo` magic value and compare `KBDLLHOOKSTRUCT.dwExtraInfo` in the hook; `LLKHF_INJECTED` alone only says "not from the keyboard driver". Neither `keyboard` nor `pynput` reads `dwExtraInfo`, so a ctypes/pywin32 hook is needed for that.
- [DEDUCTION] If the worker runs at a lower integrity level than the game (e.g. game elevated), `SendInput` is blocked by UIPI silently; if higher, injections carry `LLKHF_INJECTED` only (bit 1 clear). The game can therefore tell injected from physical if it inspects these bits or uses Raw Input.
- [DEDUCTION] `keyboard`'s `fake_alt` filter is specifically about suppressing fake-ALT events; relying on `keyboard` for physical-vs-injected discrimination is not possible without patching, and its unchecked `SetWindowsHookEx` return means a failed install is invisible.

### Gaps
- Microsoft does not publish the default `LowLevelHooksTimeout`; 300 ms rests on AutoHotkey's statement. [COMM only]
- The exact tagged source for `keyboard` 0.13.5 vs `master` was not diffed; line-level behaviour cited is from `master`.
- pynput's handling of Python exceptions inside the hook relative to the timeout (e.g. GIL contention from another Python thread delaying the callback) is not documented anywhere I found. [UNVERIFIED]

## KQ4. Injected key-release safety (SendInput KEYEVENTF_KEYUP on a key the user physically holds)

### Takeaway
Microsoft documents that `SendInput` "does not reset the keyboard's current state" and that already-pressed keys "might interfere" with generated events, recommending `GetAsyncKeyState` checks; it does not explicitly state that the OS keeps a single merged per-virtual-key state. That merging is a deduction (supported by Raymond Chen's description of the Raw Input Thread modifying "the input state"), so "release only what we pressed and the user does not hold" must be implemented with the LL hook's record of physical (non-injected) down/up events, not with `GetAsyncKeyState`.

### Cited Findings
- [DOC] "The SendInput function inserts the events in the INPUT structures serially into the keyboard or mouse input stream. These events are not interspersed with other keyboard or mouse input events inserted either by the user (with the keyboard or mouse) or by calls to keybd_event, mouse_event, or other calls to SendInput." — [SendInput (updated 2025-07-01)](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)
- [DOC] "This function does not reset the keyboard's current state. Any keys that are already pressed when the function is called might interfere with the events that this function generates. To avoid this problem, check the keyboard's state with the GetAsyncKeyState function and correct as necessary." — same page.
- [DOC] Return: "the number of events that it successfully inserted into the keyboard or mouse input stream. If the function returns zero, the input was already blocked by another thread." — same page.
- [DOC] `GetAsyncKeyState`: "The most significant bit of the return value is set if the specified key is currently down." The LSB "pressed since last call" bit "should not be relied upon because it can report false negatives." Left/right-distinguishing VKs (`VK_LSHIFT`, etc.) are supported. Returns 0 on failure (not active desktop, UIPI, desktop access). — [GetAsyncKeyState (updated 2026-01-29)](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getasynckeystate)
- [DOC] LowLevelKeyboardProc: the hook "is called before the asynchronous state of the key is updated", so `GetAsyncKeyState` inside the hook reflects the *previous* state. — [LowLevelKeyboardProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc)
- [DOC] Raymond Chen: SendInput → hardware input queue → Raw Input Thread → low-level hooks → "allowed to modify the input state". — [oldnewthing 2014-02-13](https://devblogs.microsoft.com/oldnewthing/20140213-00/?p=1773)
- [COMM] (search snippet only, page not opened) An AutoHotkey forum thread reported a physically held key's state looking wrong after a script sent hotkeys; cause not established. Not relied on.

### Inferences
- [DEDUCTION] Since `GetAsyncKeyState` exposes one down/up bit per virtual key and `SendInput` events enter the same stream as user input, there is no OS-level distinction between "down because the user holds it" and "down because we injected it": an injected KEYUP for a physically held key will flip the async state to up (and deliver WM_KEYUP / raw-input "break" to the game) until the keyboard's next hardware event for that key (typically the user's actual release, which then arrives as a redundant up, or typematic repeat if the key auto-repeats). **This is a deduction; Microsoft does not state it explicitly.**
- [DEDUCTION] Therefore the worker must maintain its own two tables from the LL hook: `physical_down[vk]` (events with `LLKHF_INJECTED` clear) and `ours_down[vk]` (events whose `dwExtraInfo` equals our magic). On stop/focus-loss, release only `ours_down − physical_down`. If the user physically holds a key we also injected, leave it down and mark it "owned by user"; it will naturally release on the user's key-up.
- [DEDUCTION] Because the hook sees events before the async state updates, the hook tables (not `GetAsyncKeyState`) are the consistent source of truth; `GetAsyncKeyState` can be used only as a post-hoc sanity check after a short delay (Chen's queue latency).
- [DEDUCTION] Use scan codes (`KEYEVENTF_SCANCODE`) and the extended flag consistently for both down and up, so the game and the OS pair the release with the press (community lore, see KQ5 snippet; MS docs do not say games require scancodes).

### Gaps
- No Microsoft text explicitly stating that injected and physical key states are merged into one per-VK state. [DEDUCTION only]
- Behaviour of typematic auto-repeat after an injected key-up on a physically held key (does the keyboard's repeat re-assert "down"?) is undocumented. [UNVERIFIED]

## KQ6. Pipes/IPC and process lifecycle in frozen apps (stdio in windowed builds, multiprocessing spawn, named vs anonymous pipes, EOF/handle inheritance, terminate vs graceful, CTRL_BREAK, Job Objects, heartbeat)

### Takeaway
In a PyInstaller `--noconsole` build `sys.stdin/stdout/stderr` are `None`; `multiprocessing` with spawn re-executes `sys.executable` with `--multiprocessing-fork` when `sys.frozen` is set, so `freeze_support()` must run first or the GUI relaunches endlessly (PyInstaller 6.9+ also needs `PYINSTALLER_RESET_ENVIRONMENT=1` for children meant to be independent). A pipe reader only sees EOF when every write handle — including any inherited copy — is closed, which is why Microsoft's sample closes the parent's copies and marks the parent's ends non-inheritable; Python's `close_fds=True` default on Windows (3.7+) plus `handle_list` limits leaks. For parent-loss cleanup, a Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` kills the worker when the GUI's last job handle closes (including on crash).

### Cited Findings

**Windowed/frozen stdio**
- [DOC] PyInstaller (stable = 6.22.3): with `--noconsole` on Windows the standard I/O objects "are unavailable, and are set to None"; code touching them raises `AttributeError`; recommended fix is to check for `None` (as under `pythonw.exe`), or set dummy file handles at startup. — [PyInstaller: Common Issues and Pitfalls](https://pyinstaller.org/en/stable/common-issues-and-pitfalls.html); version from [pyinstaller.org/en/stable](https://pyinstaller.org/en/stable/)
- [DOC] Nuitka: `--windows-console-mode` with modes `force` (default), `disable`, `attach`, `hide`; "compiled programs open a console window by default"; `disable` "Prevents a console window from opening. Use this for GUI programs that do not require console interaction." and "corresponds to using pythonw.exe". The manual page I opened does not document `sys.frozen`, multiprocessing, or stdio-being-None. — [Nuitka User Manual](https://nuitka.net/user-documentation/user-manual.html)

**multiprocessing / spawn in frozen apps**

### Inferences
- [DEDUCTION] For a `--noconsole` GUI parent, do not use `stdin=PIPE/stdout=PIPE` on the *worker* for control traffic if the GUI's own stdio is `None` and logging might print; prefer an explicit `multiprocessing.connection.Listener(r'\\.\pipe\PadTape-<pid>-<rand>', authkey=...)` named pipe (or an anonymous pipe passed via `handle_list`) so the control channel is independent of console/stdio state. Stdout/stderr of the worker should be redirected to a file or `DEVNULL` to avoid both the `None`-handle pitfall and the pipe-buffer deadlock.
- [DEDUCTION] EOF ordering: the GUI will only observe EOF on the worker's output pipe after *every* handle to the write end is closed — the worker's own, and any copy accidentally inherited by a third process the GUI spawned concurrently (Python's warning about concurrent `os.system()` style launches). Spawn the worker with `close_fds=True` (default) and never spawn other children with inheritable handles while a worker launch is in flight. Conversely, the worker detects parent death by EOF on its *input* pipe only if the GUI's write handle has not leaked into another process.
- [DEDUCTION] Graceful shutdown ladder: (1) send a `STOP` message over the pipe and wait for the worker's "released keys" ack; (2) if the worker was created with `CREATE_NEW_PROCESS_GROUP` *and it is a console-subsystem exe sharing a console* send `CTRL_BREAK_EVENT` — note this is useless for a `CREATE_NO_WINDOW`/`DETACHED_PROCESS` worker with no shared console (GenerateConsoleCtrlEvent only reaches processes sharing the caller's console); (3) `terminate()` as last resort, accepting that `TerminateProcess` runs no cleanup — so keys pressed by the worker may remain logically down; the GUI must then perform a best-effort release itself (it knows the script).
- [DEDUCTION] Parent-loss: put the worker in a Job with `KILL_ON_JOB_CLOSE | DIE_ON_UNHANDLED_EXCEPTION`; keep the job handle in the GUI process for its lifetime; the OS closes it on GUI crash and the worker is killed. Because the child "inherits the association with a job", if the GUI itself is already in a job (e.g. launched by some launcher/IDE) without breakaway rights, `AssignProcessToJobObject` can fail on older Windows; nested jobs are allowed on Windows 8+ (community claim, not opened — [UNVERIFIED]). A kill-on-close job again leaves injected keys down → the worker should additionally run a heartbeat (see below).
- [DEDUCTION] Heartbeat: GUI → worker `PING` every ~250–500 ms over the pipe; worker releases all `ours_down − physical_down` keys and exits if no ping for N intervals or on pipe EOF/`BrokenPipeError`; worker → GUI status every tick so the GUI can detect a hung worker (hook thread alive flag, last injection timestamp) and escalate to terminate + its own release pass. This complements, not replaces, the Job Object (which handles the GUI-crash case but cannot release keys).

### Gaps
- Nuitka's handling of `multiprocessing` spawn / `sys.frozen` / onefile `sys.executable` is not in the user-manual page I opened; Nuitka documents a `multiprocessing` plugin elsewhere but I did not verify it. [UNVERIFIED]
- Nothing opened confirms nested-job support on Windows 8+ (needed if the GUI already runs inside a job). [UNVERIFIED]
- Whether PyInstaller's `--noconsole` worker built from the same executable gets `CREATE_NO_WINDOW` semantics automatically (it is a GUI-subsystem exe, so no console host is created) is a deduction from the flag definition, not a PyInstaller statement.

## KQ7. Process priority / foreground boost (Programs vs Background services, Win32PrioritySeparation) and impact on a background worker competing with a game

### Takeaway
Windows boosts the foreground NORMAL-class process's priority class (and, per the legacy Win32PrioritySeparation setting defaulting to "Applications"/0x26, gives foreground threads up to 3× the quantum of background threads); a background worker process therefore runs at a scheduling disadvantage against a foreground game unless it raises its own thread priority (TIME_CRITICAL = 15 in NORMAL class, or MMCSS categories).

### Cited Findings
- [DOC] "When a process that uses NORMAL_PRIORITY_CLASS is brought to the foreground, the scheduler boosts the priority class of the process associated with the foreground window, so that it is greater than or equal to the priority class of any background processes. The priority class returns to its original setting when the process is no longer in the foreground." "When a window receives input, such as timer messages, mouse messages, or keyboard input, the scheduler boosts the priority of the thread that owns the window." "When the wait conditions for a blocked thread are satisfied, the scheduler boosts the priority of the thread." Boosts decay one level per time slice back to base; threads with base 16–31 are never boosted. `SetProcessPriorityBoost`/`SetThreadPriorityBoost` disable boosting. — [Priority Boosts (ms.date 2025-07-14)](https://learn.microsoft.com/en-us/windows/win32/procthread/priority-boosts)
- [DOC] (legacy, Windows 2000-era, archived) `HKLM\SYSTEM\CurrentControlSet\Control\PriorityControl\Win32PrioritySeparation`, REG_DWORD, range 0x0–0x3F, default 0x2; 6-bit mask AABBCC: AA interval length (short/long), BB variable vs fixed, CC foreground:background quantum ratio (00 equal/fixed, 01 2:1, 10/11 3:1). Performance Options → "Applications" sets 100110 (0x26: "short, variable length processor intervals in which foreground processes get three times as much processor time as do background processes"); "Background services" sets 011000 (0x18: "longer, fixed-length processor intervals in which foreground processes and background processes get equal processor priority"). — [Win32PrioritySeparation (TechNet archive, ms.date 2008-09-10)](https://learn.microsoft.com/en-us/previous-versions/cc976120(v=technet.10)) — note this is Windows 2000 documentation; no current Microsoft Learn page for the value was found.
- [DOC] `SetForegroundWindow` doc: "The system assigns a slightly higher priority to the thread that created the foreground window than it does to other threads." — [SetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow)
- [DOC] MMCSS factors in "Whether the application is in the foreground"; Medium category (16–22) is "part of the application that is in the foreground". — [MMCSS](https://learn.microsoft.com/en-us/windows/win32/procthread/multimedia-class-scheduler-service)
- [DOC] Priority classes and the base-priority table (NORMAL+TIME_CRITICAL=15; HIGH+NORMAL=13; REALTIME discouraged). — [Scheduling Priorities](https://learn.microsoft.com/en-us/windows/win32/procthread/scheduling-priorities)
- [COMM] Blur Busters forum posts and university slides describing Win32PrioritySeparation on modern Windows exist in search results but were not opened; the exact current-Windows semantics (and whether the quantum multiplier is applied on Windows 10/11 client exactly as in the 2000 doc) are not confirmed by a current Microsoft page. [UNVERIFIED]

### Inferences
- [DEDUCTION] With the default "Applications" setting the game (foreground, NORMAL class) gets a priority-class boost and ~3× quantum relative to the worker; if the game saturates all cores, a worker thread at NORMAL/THREAD_PRIORITY_NORMAL (base 8, boosted when its wait completes) can be delayed by up to a quantum per core before its timer-wake runs. Setting the worker's injection thread to `THREAD_PRIORITY_TIME_CRITICAL` (base 15 — above any boosted NORMAL-class game thread, below MMCSS Medium/High) is the documented, non-REALTIME way to win the scheduling race; `SetPriorityClass(HIGH_PRIORITY_CLASS)` for the whole worker is discouraged for extended running but acceptable for a process "that has all of its threads blocked most of the time".
- [DEDUCTION] If the game uses MMCSS "Games" (Medium, 16–22 while foreground), the worker at 15 still loses to those threads; only MMCSS Pro Audio (High 23–26) or REALTIME class would beat them, both inadvisable. In practice the worker wakes only briefly every 10 ms, so the "wait satisfied" boost plus TIME_CRITICAL should suffice on a machine with ≥1 spare logical core; on a fully saturated machine, jitter in the quantum range (ms) is unavoidable. (Measurement, not documentation, decides this; see KQ8.)

### Gaps
- No current Microsoft Learn page documents Win32PrioritySeparation semantics for Windows 10/11; the only official text is the Windows 2000 resource-kit entry. Treat specific quantum numbers as legacy.
- Default quantum lengths on Windows 10/11 client are not stated in any page opened.

## KQ8. Measurement separation: submission latency, OS delivery latency, game-consumption latency; timestamp resolutions

### Takeaway
Three independent clocks/observations are needed: QPC (`time.perf_counter`) around `SendInput` for submission latency; the LL hook's `KBDLLHOOKSTRUCT.time` (= `GetMessageTime` semantics, milliseconds since boot, tick-count resolution typically 10–16 ms) plus the hook callback's own QPC timestamp for OS delivery; and a game-side observer (Openplanet plugin or frame-timed screen capture) for consumption. The hook `time` field is too coarse for sub-10 ms attribution; use the hook's QPC-at-callback instead and treat `time` as a sanity cross-check.

### Cited Findings
- [DOC] `KBDLLHOOKSTRUCT.time`: "The time stamp for this message, equivalent to what GetMessageTime would return for this message." — [KBDLLHOOKSTRUCT](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-kbdllhookstruct)
- [DOC] `GetMessageTime`: "The time is a long integer that specifies the elapsed time, in milliseconds, from the time the system was started to the time the message was created (that is, placed in the thread's message queue)." Wraps; "subtract the time of the first message from the time of the second message (ignoring overflow)". — [GetMessageTime (updated 2025-07-01)](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getmessagetime)
- [DOC] `GetTickCount`: "The resolution of the GetTickCount function is limited to the resolution of the system timer, which is typically in the range of 10 milliseconds to 16 milliseconds." Wraps at 49.7 days; use `GetTickCount64` or a high-resolution timer for finer needs. — [GetTickCount (updated 2025-07-01)](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-gettickcount) — Note: Microsoft does not state on the pages opened that message/hook `time` is derived from the tick count; both are "milliseconds since system start", which makes the same resolution caveat the conservative assumption. [DEDUCTION]
- [DOC] `SendInput` returns the number of events inserted; events are inserted "serially into the keyboard or mouse input stream". — [SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)
- [DOC] Raymond Chen: injected input is queued and processed by the Raw Input Thread, which first runs all low-level hooks, then updates input state; so the LL hook callback time is an upper bound on "OS accepted the event" and precedes async-state update and delivery to the target thread's queue. — [oldnewthing 2014-02-13](https://devblogs.microsoft.com/oldnewthing/20140213-00/?p=1773)
- [DOC] `timeBeginPeriod`: "Setting a higher resolution does not improve the accuracy of the high-resolution performance counter." (QPC is independent of timer resolution.) — [timeBeginPeriod](https://learn.microsoft.com/en-us/windows/win32/api/timeapi/nf-timeapi-timebeginperiod)
- [DOC] Python `time.sleep` Windows note: "resolution of 100 nanoseconds" for the timer itself; the suspension "may be longer than requested by an arbitrary amount". — [time docs](https://docs.python.org/3/library/time.html)
- [MEAS] Reference figures for the sleep leg: Go commit table (≈1.08 ms for a 1 ms request with the high-res flag; ≈4 ms without flag and without timeBeginPeriod) and CPython issue comments (Py3.11 `sleep(0.001)` mean 1.6 ms). — [Go commit](https://go.googlesource.com/go/+/515e6a9b12dfe654c86cfd070ee5d6ac144fe116), [gh-65501](https://github.com/python/cpython/issues/65501)
- [COMM] (search snippet only; repo not opened) amitxv/TimerResolution ships a `MeasureSleep` tool for measuring `Sleep(1)` precision with mean/stddev. [github.com/amitxv/TimerResolution](https://github.com/amitxv/TimerResolution)

### Inferences
- [DEDUCTION] Instrumentation plan per injected event, all in the worker: `t0 = perf_counter()` immediately before `SendInput`; `t1` after it returns (submission latency = t1 − t0, normally microseconds); the LL hook thread records `t2 = perf_counter()` when it sees the event with our `dwExtraInfo` magic (OS delivery latency to the hook ≈ t2 − t0, which also captures scheduling delay of the hook thread itself — so pin the hook thread at high priority and keep its callback trivial); also log `KBDLLHOOKSTRUCT.time` and `GetTickCount64()` for cross-checking at ms granularity only. Deadline error = t0 − scheduled_deadline (the sleep/scheduling leg).
- [DEDUCTION] Game-consumption latency cannot be observed from the worker; it requires a game-side probe (an Openplanet script logging input state per frame against a shared clock, or a frame-timed capture) and must be reported separately; the LL hook timestamp is the last point in the OS pipeline the worker can see before the game's own queue/raw-input processing.
- [DEDUCTION] Because the hook is invoked for *physical* events too, the same hook gives physical-input timestamps for the takeover detector with the same QPC clock, allowing "time from physical keypress to our release of injected keys" to be measured end-to-end inside the worker.

### Gaps
- No Microsoft page opened states the exact clock source/resolution of `KBDLLHOOKSTRUCT.time`/`GetMessageTime` beyond "milliseconds since system start"; the 10–16 ms resolution is carried over from `GetTickCount` by analogy. [DEDUCTION]
- No published, reputable end-to-end measurement of SendInput → LL hook → game frame latency on Windows 10/11 was found in this pass.
