# Windows input-injection atomicity and timing guarantees (SendInput, XInput, virtual gamepads, DirectInput, Raw Input, timers)

Research date: 2026-10-20. Every claim is tagged:
- **[DOC]** documented by Microsoft Learn or the project's own docs (URL + doc date given).
- **[SRC]** read from source code (URL + commit/archive date given). Where a source file was read through an automated summariser rather than line-by-line, this is noted as "(summarised read)" and the key lines are quoted so an engineer can grep for them.
- **[COMMUNITY]** forum / blog / third-party inference.
- **[UNVERIFIED]** nothing authoritative found; stated as such.

Only URLs that were actually opened are cited. Where a search snippet was seen but the page was not opened, that is said explicitly and the item is treated as unverified.

Headline for the engineer (details and citations in the sections below):

1. `SendInput` guarantees only that the INPUT array is *inserted* serially and not interleaved with other input. It says nothing about atomic *consumption*: the receiving game dequeues messages / updates key-state one event at a time, so "several key changes submitted together" can be observed split by a poller that reads between two events. [DOC]
2. `XInputGetState` is a pure snapshot API: there is no event queue; `dwPacketNumber` only tells you *whether* state changed since the last poll, not how many times. Intermediate states between two polls are unobservable. `XInputSetState` is vibration only. [DOC]
3. A ViGEmBus virtual Xbox 360 pad is fed by `vigem_target_x360_update`, which submits one complete `XUSB_REPORT` per call through a blocking (`GetOverlappedResult(..., TRUE)`) IOCTL. The driver compares the new report with the last delivered one, ignores identical reports, and completes exactly one pending interrupt-IN read with it; if no read is pending at that instant the report is not cached (it is dropped and the IOCTL fails with a status the client library does not surface). So each successful `update()` is one whole-report state change, never a partial one. [SRC]
4. ViGEmBus is retired/archived (Nov 2 2023). Nefarius' own docs now list a *commercial* "VirtualPad" framework for business partners; no open-source successor was found. The last signed ViGEmBus setup is 1.22.0 (driver unchanged from 1.21.442). [DOC]
5. DirectInput keyboard/mouse on modern Windows is implemented on top of Raw Input (`WM_INPUT`) in a second thread; buffered `GetDeviceData` carries a ms `dwTimeStamp` from the `GetTickCount`/`timeGetTime` clock and a global `dwSequence`. Buffer size must be set via `DIPROP_BUFFERSIZE`; overflow returns `DI_BUFFEROVERFLOW`. [DOC]
6. Raw Input gives no device timestamp; the only time is `GetMessageTime` (ms, system tick). [DOC]
7. Timer resolution: `timeBeginPeriod` stopped being global in Windows 10 2004; Windows 11 may ignore a process's request when its windows are occluded/minimised and inaudible; opt out with `SetProcessInformation(ProcessPowerThrottling, PROCESS_POWER_THROTTLING_IGNORE_TIMER_RESOLUTION)` (StateMask 0); `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION` exists since Windows 10 1803. [DOC]

## Key question 1 — SendInput: what exactly is guaranteed, and how injected keys reach the game (messages, GetAsyncKeyState, Raw Input, DirectInput, low-level hooks)

### Takeaway
Microsoft guarantees serial, non-interleaved *insertion* of the INPUT array into the system input stream and nothing about how the receiving thread consumes it. Consumption is per event (one message / one key-state update at a time), so a game that polls `GetAsyncKeyState` or pumps messages can observe a batch half-applied. Injected keyboard events are visible to `WH_KEYBOARD_LL` hooks with `LLKHF_INJECTED` (documented); whether they appear in Raw Input with a NULL `hDevice` is **not** documented by Microsoft.

### Cited Findings

**SendInput insertion guarantee (exact text)**
- "The **SendInput** function inserts the events in the INPUT structures serially into the keyboard or mouse input stream. These events are not interspersed with other keyboard or mouse input events inserted either by the user (with the keyboard or mouse) or by calls to keybd_event, mouse_event, or other calls to **SendInput**." [DOC] — [SendInput function (winuser.h)](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput) (ms.date 2018-12-05, updated_at 2025-07-01, git_commit_id fa53641576e3603fa7b66d3a4ad969d3ce49d6f3)
- Return value: "the number of events that it successfully inserted into the keyboard or mouse input stream. If the function returns zero, the input was already blocked by another thread." "This function fails when it is blocked by UIPI. Note that neither GetLastError nor the return value will indicate the failure was caused by UIPI blocking." "Applications are permitted to inject input only into applications that are at an equal or lesser integrity level." [DOC] — same page.
- "This function does not reset the keyboard's current state. Any keys that are already pressed when the function is called might interfere with the events that this function generates. To avoid this problem, check the keyboard's state with the GetAsyncKeyState function and correct as necessary." [DOC] — same page.
- The page contains **no** statement about atomic consumption, about the receiving thread seeing the events in one message-loop iteration, or about key-state tables being updated atomically for the batch. Confirmed by reading the full page. [DOC, absence] — same page.
- Keyboard Input Overview restates it as: "The **SendInput** function works by injecting a series of simulated input events into a device's input stream. The effect is similar to calling the keybd_event or mouse_event function repeatedly, except that the system ensures that no other input events intermingle with the simulated events." [DOC] — [Keyboard Input Overview](https://learn.microsoft.com/en-us/windows/win32/inputdev/about-keyboard-input) (ms.date 2025-07-14, updated_at 2026-07-08, commit b584d62f251cdc042d3f1593417c724877cf69d5)

Eventually, the thread's message loop removes the message and passes it to the appropriate window procedure for processing." [DOC] — Keyboard Input Overview (above).

Releasing a key cannot start the automatic repeat feature, so the repeat count for WM_KEYUP and WM_SYSKEYUP messages is always set to 1." [DOC] — same page.

- "Internally, DirectInput creates a second thread to read WM_INPUT data, and using the DirectInput APIs will add more overhead than simply reading WM_INPUT directly... ### Inferences
- Atomicity: Because insertion is serial and consumption is per event, a SendInput batch of N events is seen by the game as N ordered events with no interleaved foreign input, but there is no barrier preventing the game from polling between event k and k+1. For a message-pumping game, all N messages are normally already in its queue by the time its next pump runs (they were inserted back-to-back by one kernel call), so in practice they land in one frame; for a `GetAsyncKeyState` poller running on another thread, a poll can land between two async-table updates. Nothing in the docs forbids this. [inference from DOC]
- Because `GetKeyboardState`/`GetKeyState` are updated only as the thread *removes* messages, a game using those sees the batch exactly at message-pump granularity; a game using `GetAsyncKeyState` sees it at event granularity. [inference from DOC]
- DirectInput keyboard (`GetDeviceState`/`GetDeviceData` on `GUID_SysKeyboard`) on Windows 10/11 is a Raw Input consumer, so injected keys are visible to it iff they are visible in Raw Input. That SendInput keys reach DirectInput games is common experience and the 2010 SO report shows injected input producing `WM_INPUT` for mouse, but Microsoft does not document it. [COMMUNITY inference]
- UIPI: if the game runs elevated (or the launcher elevates it), an unelevated injector's `SendInput` silently fails (returns 0 or less than cInputs with no UIPI-specific error). [inference from DOC]

### Gaps
- No Microsoft statement found on whether SendInput-injected keyboard events appear in `WM_INPUT` and, if so, what `hDevice` they carry (NULL vs. some handle). The only documented NULL case is the precision touchpad. **UNVERIFIED**; test empirically (`GetRawInputData` + log `header.hDevice` and `ExtraInformation` while injecting with a distinctive `dwExtraInfo`).
- No Microsoft statement found on whether `RAWKEYBOARD.ExtraInformation` carries the `KEYBDINPUT.dwExtraInfo` value for injected events. UNVERIFIED (OSR thread asked the equivalent driver-level question and got no answer).
- Whether a caller-supplied non-zero `KEYBDINPUT.time` is used for ordering or merely copied into `GetMessageTime` is undocumented. UNVERIFIED.

## Key question 2 — Key auto-repeat with SendInput; which state API the game uses

### Takeaway
Microsoft attributes auto-repeat to "the keyboard's automatic repeat feature" (generated below the point where SendInput enters); no Microsoft page says SendInput key-down generates typematic repeats, and community/driver-level statements say injected events bypass the keyboard driver stack. Which API a given game uses to read keys is game-specific and unknown.

### Cited Findings
- "if the user holds down a key long enough to start the keyboard's automatic repeat feature, the system generates a number of WM_KEYDOWN or WM_SYSKEYDOWN messages in a row." Previous-key-state flag (KF_REPEAT): "set to 1 for WM_KEYDOWN and WM_SYSKEYDOWN keystroke messages generated by the automatic repeat feature." [DOC] — [Keyboard Input Overview](https://learn.microsoft.com/en-us/windows/win32/inputdev/about-keyboard-input)
- `KEYBDINPUT` and `SendInput` pages contain no mention of auto-repeat. [DOC, absence] — [KEYBDINPUT](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-keybdinput), [SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)
- "The injected events don't go through keyboard driver." [COMMUNITY] — [OSR thread](https://community.osr.com/t/keyboard-filter-driver-identify-injected-input-sendinput/52509) (Alex_Grig, 2016-03-02)
- DirectInput "Keyboard Data" lists "character repeat" among services provided by Windows messages (i.e., repeats are a message-layer/driver artefact, not something DirectInput synthesises). [DOC] — [Keyboard Data](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee418640(v=vs.85))

### Inferences
- A single SendInput key-down does **not** produce repeated WM_KEYDOWN messages; the injector must hold state itself (the game sees the key as held via `GetAsyncKeyState`/Raw Input make without break until an explicit key-up). This is the universally observed behaviour and consistent with "injected events don't go through keyboard driver", but Microsoft does not state it. [COMMUNITY inference]
- If the key-down is injected with `KEYEVENTF_SCANCODE`, the game sees a layout-independent scan code, which matters for AZERTY vs QWERTY bindings (the keyboard overview explicitly gives WASD/AZERTY as the use case for scan codes). [inference from DOC]

### Gaps
- Which API the target game uses (`GetAsyncKeyState`, `WM_KEYDOWN`, Raw Input, DirectInput `GetDeviceState`, DirectInput buffered) is **game-specific unknown**. UNVERIFIED.

## Key question 3 — XInput semantics: XInputGetState, dwPacketNumber, XInputSetState, polling advice, DLL versions

### Takeaway
XInput is poll-only: `XInputGetState` returns the current state; `dwPacketNumber` "is incremented only if the status of the controller has changed since the controller was last polled" and only tells you *whether* something changed. There is no queue, so any state that exists only between two polls is lost. `XInputSetState` is documented as vibration only. Microsoft's guidance is "from frame to frame... state should be retrieved"; no numeric poll-rate is given.

### Cited Findings
- `XInputGetState`: "Retrieves the current state of the specified controller." `dwUserIndex` "Can be a value from 0 to 3." Returns `ERROR_SUCCESS`, `ERROR_DEVICE_NOT_CONNECTED`, or a Winerror code; "The function does not use **SetLastError**". DLLs: "Xinput1_4.dll; Xinput9_1_0.dll; Xinputuap.dll"; api_location also lists "Ext-MS-Win-Gaming-XInput-L1-1-0.dll". Platform requirements: "Windows 8 (XInput 1.4), DirectX SDK (XInput 1.3), Windows Vista (XInput 9.1.0)". [DOC] — [XInputGetState](https://learn.microsoft.com/en-us/windows/win32/api/xinput/nf-xinput-xinputgetstate) (updated_at 2024-02-22)
- `XINPUT_STATE.dwPacketNumber`: "State packet number. The packet number indicates whether there have been any changes in the state of the controller. If the *dwPacketNumber* member is the same in sequentially returned **XINPUT_STATE** structures, the controller state has not changed." Remarks: "The *dwPacketNumber* member is incremented only if the status of the controller has changed since the controller was last polled." [DOC] — [XINPUT_STATE](https://learn.microsoft.com/en-us/windows/win32/api/xinput/ns-xinput-xinput_state) (updated_at 2024-02-22)
- Getting Started: "From frame to frame in a game application, state should be retrieved and game information updated to reflect the controller changes." "The *dwPacketNumber* member... can be used to check if the state of the controller has changed since the last call to **XInputGetState**. If *dwPacketNumber* does not change between two sequential calls to **XInputGetState**, then there has been no change in state. If it differs, then the application should check the *Gamepad* member". "For performance reasons, don't call **XInputGetState** for an 'empty' user slot every frame. We recommend that you space out checks for new controllers every few seconds instead." [DOC] — [Getting Started With XInput](https://learn.microsoft.com/en-us/windows/win32/xinput/getting-started-with-xinput) (ms.date 2025-07-14, updated_at 2026-05-13, commit d4d9b83e8a450b1fbc2bd0442b272da0a1045468)
- Multiple controllers: "This ID will be in the range of 0-3 and is set automatically by XInput. The number corresponds to the port that the controller is plugged into, and is not modifiable." [DOC] — same page.
- `XInputSetState`: "Sends data to a connected controller. This function is used to activate the vibration function of a controller." Parameter is `XINPUT_VIBRATION*`. [DOC] — [XInputSetState](https://learn.microsoft.com/en-us/windows/win32/api/xinput/nf-xinput-xinputsetstate) (updated_at 2024-02-22)
- Versions: "XInput 1.4 ships today as a system component in Windows 8 as XINPUT1_4.DLL. It is available 'inbox' and does not require redistribution". "XInput 9.1.0 ships today as a system component in Windows 10, Windows 8.x, Windows 7, and Windows Vista as XINPUT9_1_0.DLL. It is maintained primarily for backward compatibility... reduced function set"; in 9.1.0 "XInputEnable, XInputGetBatteryInformation, and XInputGetKeystroke functions are not available" and `XInputGetCapabilities` returns fixed data. "The last version to ship in the DirectX SDK was XInput 1.3, available in the June 2010 release of the legacy DirectX SDK." [DOC] — [XInput Versions](https://learn.microsoft.com/en-us/windows/win32/xinput/xinput-versions) (ms.date 2025-07-14, updated_at 2025-07-16)
- XInput devices in DirectInput: "All XInput devices will show up as both XInput and DirectInput devices"; "The left and right trigger buttons will act as a single button, not independently"; "The vibration effects will not be available". The page also carries a banner pointing to the GDK GameInput API as "the next-generation input API". [DOC] — [Comparison of XInput and DirectInput features](https://learn.microsoft.com/en-us/windows/win32/xinput/xinput-and-directinput) (ms.date 2025-07-14, updated_at 2025-07-16)

### Inferences
- Because `dwPacketNumber` is defined only as "changed since last poll", it cannot be used to count how many distinct reports occurred between two polls; a game polling at 60 Hz against a feeder updating at 100 Hz will miss ~40 % of reports with no indication. [inference from DOC]
- Microsoft gives no statement on increment granularity (per USB report vs per polled change) — see Gaps.

### Gaps
- No Microsoft statement on *where* `dwPacketNumber` is generated (xinput1_4.dll vs. the XUSB kernel stack) or whether it increments once per received USB report or once per observed change. UNVERIFIED.
- No Microsoft numeric polling-frequency recommendation beyond "frame to frame". UNVERIFIED (none exists on the pages opened).

## Key question 4 — Virtual gamepads: ViGEmBus/ViGEmClient (`vigem_target_x360_update` semantics, status 2023–2026, successors), vJoy, ScpVBus, vgamepad (`update()` blocking?)

### Takeaway
`vigem_target_x360_update` sends one complete 12-byte `XUSB_REPORT` per call via a synchronous (`GetOverlappedResult(..., TRUE)`) IOCTL; the bus driver forwards it only if it differs from the last delivered report, and only by completing one pending interrupt-IN read (no cache/coalesce when none is pending). There is no rate limiter in client or driver. ViGEmBus and ViGEmClient are archived (Nov 2 and Sep 8 2023); Nefarius now offers a commercial "VirtualPad" framework to business partners; no open-source successor exists. vgamepad 0.1.3 (Feb 2026) still bundles the ViGEmBus 1.17.333 MSI and calls `vigem_target_x360_update` directly from `update()`.

## Key question 7 — DirectInput buffered data: GetDeviceData, DIDEVICEOBJECTDATA (dwTimeStamp, dwSequence), DIPROP_BUFFERSIZE, DI_BUFFEROVERFLOW; which devices; clock source

### Takeaway
Buffered DirectInput data exists for keyboard, mouse and joystick devices alike; each event carries `dwTimeStamp` (ms, "same clock used by the Microsoft Win32 GetTickCount or timeGetTime functions, but it produces potentially more precise values") and a single global `dwSequence`. Buffering is off until `DIPROP_BUFFERSIZE` is set (otherwise `DIERR_NOTBUFFERED`); the buffer holds "one less than the buffer size"; overflow is signalled by `DI_BUFFEROVERFLOW`. Immediate `GetDeviceState` is a snapshot.

### Cited Findings
- `GetDeviceData`: "Retrieves buffered data from the device." `DIGDD_PEEK` "Do not remove the items from the buffer." Return "DI_OK or DI_BUFFEROVERFLOW"; errors "DIERR_INPUTLOST, DIERR_INVALIDPARAM, DIERR_NOTACQUIRED, DIERR_NOTBUFFERED, DIERR_NOTINITIALIZED". "If the method returns DI_BUFFEROVERFLOW, the data in the rgdod array has been truncated." "Before device data can be obtained, you must set the data format and the buffer size by using the IDirectInputDevice8::SetDataFormat and IDirectInputDevice8::SetProperty methods". "The maximum number of events that the buffer will hold is one less than the buffer size set with the IDirectInputDevice8::SetProperty method." Flush: rgdod NULL + pdwInOut INFINITE; overflow query: rgdod NULL + pdwInOut 0. [DOC] — [IDirectInputDevice8::GetDeviceData](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee417894(v=vs.85)) (ms.date 2011-09-10, updated_at 2021-10-26)
- `DIDEVICEOBJECTDATA`: `dwOfs` "the offset into the current data format of the object whose data is being reported"; `dwData` "For button input, only the low byte of *dwData* is significant. The high bit of the low byte is set if the button was pressed"; `dwTimeStamp` "System time at which the input event was generated, in milliseconds. This value wraps around approximately every 50 days."; `dwSequence` "DirectInput sequence number for this event. All input events are assigned an increasing sequence number. This enables events from different devices to be sorted chronologically." Remarks: "The system time returned in *dwTimeStamp* comes from the same clock used by the Microsoft Win32 GetTickCount or timeGetTime functions, but it produces potentially more precise values. For example, on Microsoft Windows 95, the GetTickCount timer is updated only every 55 milliseconds, but the *dwTimeStamp* value is accurate to within 1 millisecond." [DOC] — [DIDEVICEOBJECTDATA](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee416611(v=vs.85))
- "The **dwTimeStamp** member contains the system time, in milliseconds, at which the event took place. This is equivalent to the value that would have been returned by the Microsoft Win32 **GetTickCount** function, but at a higher resolution." "The DirectInput system keeps a single sequence counter, which is incremented by each buffered event from any device. (Simultaneous events on the same device, such as diagonal mouse movements, increment the count only once.)" "Events are always placed in the buffer in chronological order". [DOC] — [Time Stamps and Sequence Numbers](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee418871(v=vs.85))
- "Buffered data is a record of events that are stored until an application retrieves them. Immediate data is a snapshot of the current state of a device." "For devices that do not generate interrupts, such as analog joysticks, DirectInput does not obtain any data until you call the IDirectInputDevice8::Poll method." [DOC] — [Buffered and Immediate Data](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee416236(v=vs.85))
- `DIPROP_BUFFERSIZE` is set via `DIPROPDWORD` with `dwHow = DIPH_DEVICE`; "properties can be changed only when the device is in an unacquired state" (except FF gain); example sets `dipdw.dwData = 10`. [DOC] — [Device Properties](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee416595(v=vs.85))
- `GetDeviceState`: "Retrieves immediate data from the device."; `c_dfDIKeyboard` → "array of 256 bytes". [DOC] — [IDirectInputDevice8::GetDeviceState](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee417897(v=vs.85))
- Keyboard-specific sub-pages exist for "Buffered Keyboard Data" and "Checking for Lost Keyboard Input" (listed but not opened). [DOC] — [Keyboard Data](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/ee418640(v=vs.85))
- `GetTickCount` resolution: "limited to the resolution of the system timer, which is typically in the range of 10 milliseconds to 16 milliseconds"; wraps at 49.7 days. [DOC] — [GetTickCount](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-gettickcount) (updated_at 2025-07-01)

### Inferences
- Because DirectInput keyboard/mouse is a Raw-Input consumer thread on modern Windows (see Q1), `dwTimeStamp` for keyboard events is the system tick at which DirectInput's thread processed the `WM_INPUT`, not a device clock; its precision is bounded by the system timer (and by `timeBeginPeriod` state, see Q9). [inference from DOC]
- A game reading buffered DirectInput sees SendInput batches as consecutive events with identical or near-identical `dwTimeStamp` and consecutive `dwSequence`, which is the only Windows input path giving the game an event-level ordering/timestamp of the batch. [inference from DOC]

### Gaps
- The default `DIPROP_BUFFERSIZE` value (0) is implied by `DIERR_NOTBUFFERED` but the archived property-reference page could not be located (ee416498 returned 404). Minor.

## Key question 8 — Raw Input timing (WM_INPUT, RAWKEYBOARD, GetMessageTime, RIDEV_INPUTSINK)

### Takeaway
Raw Input delivers per-event keyboard data (make/break, scan code, VKey) but no device timestamp; the only time available is `GetMessageTime`, the ms system tick at which the message was placed in the thread queue. Background delivery requires `RIDEV_INPUTSINK` with an `hwndTarget`.

### Cited Findings
- `GetMessageTime`: "The time is a long integer that specifies the elapsed time, in milliseconds, from the time the system was started to the time the message was created (that is, placed in the thread's message queue)." "does not necessarily increase between subsequent messages, because the value wraps". [DOC] — [GetMessageTime](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getmessagetime) (updated_at 2025-07-01)
- `RAWKEYBOARD` fields (no timestamp), `RAWINPUTHEADER.hDevice`, `RIDEV_INPUTSINK`, `WM_INPUT` RIM_INPUT/RIM_INPUTSINK — see Q1 citations. [DOC]
- Scan codes: "The **Scan 1 Make** code is delivered in WM_KEYDOWN/WM_KEYUP/WM_SYSKEYDOWN/WM_SYSKEYUP and WM_INPUT messages." [DOC] — [Keyboard Input Overview](https://learn.microsoft.com/en-us/windows/win32/inputdev/about-keyboard-input)
- `GetRawInputBuffer` batched read: "useful for high-frequency devices such as mice at 1000Hz, where multiple events may accumulate between message loop iterations"; `GetMessage` removes the current `WM_INPUT` so the buffer read "will not see the current event". [DOC] — [Raw Input Overview](https://learn.microsoft.com/en-us/windows/win32/inputdev/about-raw-input)

### Inferences
- A Raw-Input game can order a SendInput batch (events are distinct `WM_INPUT`s in insertion order) but cannot time it better than the message tick; sub-millisecond spacing inside a batch is invisible. [inference from DOC]

### Gaps
- None beyond the injected-`hDevice` question in Q1.

## Key question 9 — Windows timing: GetMessageTime/GetTickCount resolution, QueryPerformanceCounter, timeBeginPeriod changes (Win10 2004, Win11), CreateWaitableTimerExW high-resolution flag, SetProcessInformation power-throttling opt-out

### Takeaway
QPC is the sub-microsecond, monotonic clock ("typically... ≤ 1 µs", TSC-based, no kernel transition); tick-based clocks (GetTickCount, GetMessageTime, DirectInput dwTimeStamp) are 10–16 ms class. `timeBeginPeriod` is per-process since Windows 10 2004 and may be ignored on Windows 11 when the process's windows are occluded/minimised and inaudible; `PROCESS_POWER_THROTTLING_IGNORE_TIMER_RESOLUTION` with `StateMask = 0` forces the request to be honoured. `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION` requires Windows 10 1803+.

### Cited Findings
- `timeBeginPeriod`: "Prior to Windows 10, version 2004, this function affects a global Windows setting. For all processes Windows uses the lowest value (that is, highest resolution) requested by any process. Starting with Windows 10, version 2004, this function no longer affects global timer resolution. For processes which call this function, Windows uses the lowest value (that is, highest resolution) requested by any process. For processes which have not called this function, Windows does not guarantee a higher resolution than the default system resolution." "Starting with Windows 11, if a window-owning process becomes fully occluded, minimized, or otherwise invisible or inaudible to the end user, Windows does not guarantee a higher resolution than the default system resolution. See SetProcessInformation". "Setting a higher resolution does not improve the accuracy of the high-resolution performance counter." Must be matched with `timeEndPeriod`. [DOC] — [timeBeginPeriod](https://learn.microsoft.com/en-us/windows/win32/api/timeapi/nf-timeapi-timebeginperiod) (updated_at 2024-02-22)
- `SetProcessInformation`: "When a process opts into enabling `PROCESS_POWER_THROTTLING_IGNORE_TIMER_RESOLUTION`, any current timer resolution requests made by the process will be ignored... After explicitly disabling `PROCESS_POWER_THROTTLING_IGNORE_TIMER_RESOLUTION`, the system remembers and honors any previous timer resolution request by the process. By default in Windows 11 if a window owning process becomes fully occluded, minimized, or otherwise non-visible to the end user, and non-audible, Windows may automatically ignore the timer resolution request and thus does not guarantee a higher resolution than the default system resolution." Example "Always honor Timer Resolution Requests": `ControlMask = PROCESS_POWER_THROTTLING_IGNORE_TIMER_RESOLUTION; StateMask = 0;`. Also EcoQoS via `PROCESS_POWER_THROTTLING_EXECUTION_SPEED` ("If an application does not explicitly enable... the system will use its own heuristics"). Minimum client Windows 8. [DOC] — [SetProcessInformation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation) (ms.date 2024-10-31, updated_at 2025-07-01). Note: the `PROCESS_POWER_THROTTLING_STATE` structure page lists only `EXECUTION_SPEED` and omits the timer flag — [PROCESS_POWER_THROTTLING_STATE](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/ns-processthreadsapi-process_power_throttling_state) (updated_at 2024-02-22)
- `CreateWaitableTimerExW`: `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION` 0x00000002 "Creates a high resolution timer. Use this value for time-critical situations when short expiration delays on the order of a few milliseconds are unacceptable. This value is supported in Windows 10, version 1803, and later." [DOC] — [CreateWaitableTimerExW](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createwaitabletimerexw) (updated_at 2024-11-20)
- QPC: "When you need time stamps with a resolution of 1 microsecond or better... choose QueryPerformanceCounter"; "If resolution of 10 to 16 milliseconds is sufficient, you can use GetTickCount64, QueryInterruptTime..."; "Is the performance counter monotonic (non-decreasing)? Yes. QPC does not go backward."; "A kernel transition is not required if the system can use the TSC register as the basis for QPC"; values from different threads differing by ±1 tick have ambiguous ordering; frequency fixed at boot (10 MHz under hypervisor v1.0 interface "or always in some newer versions of Windows"); "GetTickCount and GetTickCount64 aren't related to QPC". Typical table: QPC via TSC resolution 333 ns, access 30 ns; PC RTC 15.625 ms. [DOC] — [Acquiring high-resolution time stamps](https://learn.microsoft.com/en-us/windows/win32/sysinfo/acquiring-high-resolution-time-stamps) (ms.date 2018-05-31, updated_at 2025-12-13)
- `GetTickCount` resolution "typically in the range of 10 milliseconds to 16 milliseconds". [DOC] — [GetTickCount](https://learn.microsoft.com/en-us/windows/win32/api/sysinfoapi/nf-sysinfoapi-gettickcount)
- `GetMessageTime` is ms since boot at queue-insertion time (see Q8). [DOC]

### Inferences
- An injector process that sleeps between SendInput/`update()` calls needs its own `timeBeginPeriod(1)` (per-process since 2004) or a high-resolution waitable timer; and on Windows 11 it must either keep a visible window or call `SetProcessInformation(ProcessPowerThrottling, ControlMask=IGNORE_TIMER_RESOLUTION, StateMask=0)` to keep 1 ms sleeps when the game is fullscreen and the injector is occluded. The game process itself is subject to the same rules independently. [inference from DOC]
- All Windows-side input timestamps available to a game (GetMessageTime, KBDLLHOOKSTRUCT.time, DirectInput dwTimeStamp) are tick-class (ms, 10–16 ms granularity unless the system timer is raised); only the game's own QPC reads at poll time are sub-ms. [inference from DOC]

### Gaps
- None material.

## Key question 10 — How the Trackmania RL projects actually inject (tmrl / vgamepad; Linesight)

### Takeaway
tmrl drives TM2020 through vgamepad: per control step it sets right trigger (gas), left trigger (brake) and left-stick X (steer) and calls `update()` once; rtgym enforces a nominal 50 ms (20 Hz) step with "elastic" timeouts. Linesight does not use Windows input injection at all: it drives TMNF through TMInterface (`set_input_state`) synchronised to the game's run-step callbacks (`run_steps_per_action`, 10 ms units) with the engine paused during inference.

### Cited Findings
- tmrl `control_gamepad.py` (full file opened; Windows/Linux branch): `control_gamepad(gamepad, control)` asserts controls in [-1, 1], calls `right_trigger_float` (gas or 0.0), `left_trigger_float` (brake or 0.0), `left_joystick_float(control[2], 0.0)`, then a single `gamepad.update()`. `gamepad_reset` presses B (0x2000) with `update()`, `time.sleep(0.1)`, release, `update()`. [SRC] — [tmrl/custom/tm/utils/control_gamepad.py](https://raw.githubusercontent.com/trackmania-rl/tmrl/master/tmrl/custom/tm/utils/control_gamepad.py); repo commits: 10266a7 (May 5 2025, "Release 0.7.1"), b042e9c (Mar 24 2025), dccef7c (Feb 6 2025, "Release 0.7.0") — [commits](https://github.com/trackmania-rl/tmrl/commits/master)
- tmrl README: "The example pipeline controls the game via a virtual gamepad, which enables analog actions."; rtgym time steps are "elastically constrained to their nominal duration" and otherwise "the previous time-step times out"; config `time_step_duration` 0.05 ("rtgym ensures this runs at 20Hz by default"); `time_step_timeout_factor` = "maximum elasticity of a time step". No documented timing/latency issues. [DOC] — [trackmania-rl/tmrl](https://github.com/trackmania-rl/tmrl)
- Linesight `game_instance_manager.py`: inputs sent via `self.iface.set_input_state(**config_copy.inputs[action_idx])` (TMInterface socket); `run_steps_per_action` default 10, `set_on_step_period(self.run_steps_per_action * 10)`, decision when `_time % (10 * self.run_steps_per_action) == 0`; on a decision step it gets the simulation state, pauses with `request_speed(0)`, requests a frame, runs the policy, sends the input, resumes with `request_speed(self.running_speed)`. No vgamepad, no SendInput (win32 `SendKeys("%")` is used only for window focus). [SRC] — [game_instance_manager.py raw](https://raw.githubusercontent.com/pb4git/linesight/main/trackmania_rl/tmi_interaction/game_instance_manager.py); folder contains `Python_Link.as`, `game_instance_manager.py`, `tminterface2.py` — [tmi_interaction](https://github.com/pb4git/linesight/tree/main/trackmania_rl/tmi_interaction); repo now under owner **Linesight-RL**; latest commits f6e7822 and 23aef60 (Sep 30 2026), 83656d3 (Jun 20 2026) — [commits](https://github.com/pb4git/linesight/commits/main); README: "All runs produced by this project are Tool Assisted." — [Linesight docs index](https://linesight-rl.github.io/linesight/build/html/)
- TMInterface: TMNF/TMUF only; "Full, deterministic input playback"; not for public leaderboards. [DOC] — [donadigo.com/tminterface](https://donadigo.com/tminterface/)

### Inferences
- tmrl's control path inherits every property in Q4: one whole-report change per 50 ms step, delivered into the XUSB pending read, observed by the game at its next XInput poll; there is no synchronisation between tmrl's step clock and the game's physics/render polls. [inference from SRC]
- Linesight's approach (engine-tick-synchronous input via a game-specific interface, engine paused during inference) is the only one of the two that is deterministic by construction, and it is unavailable for TM2020 (TMInterface is TMNF/TMUF-only). [inference from DOC/SRC]

### Gaps
- No tmrl/vgamepad issue-tracker threads on timing or dropped reports were found (searches returned unrelated results). UNVERIFIED whether such reports exist.
- vgamepad bundles ViGEmBus 1.17.333.0 (Windows 10-only per its release notes) while the last signed setup is 1.22.0; whether vgamepad's installer step works on current Windows 11 builds was not verified.
